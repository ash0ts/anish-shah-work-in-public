# Intent regression review

Use these scenarios when changing either repository skill. Review the actual
response/implementation; frontmatter validation alone cannot prove compliance.
These are dry-run cases, never authorization to mutate a real environment.

| Request | Required behavior | Incorrect behavior |
| --- | --- | --- |
| “Don't hide those numbers from Home.” after an older plan excluded them | Keep the requested figures visibly on Home, preserve owner-reported status, update presentation and tests | Continue enforcing the old plan; hide them in disclosures or Sources |
| “Implement a shorter metric section.” | Change the appropriate deck, manifest, and UI in the engineering lane; retain exact units and source access | Stop at an implementation-request template because a copy skill was loaded |
| “Keep WREU vague.” | Preserve the literal acronym and owner report; leave the definition/window unspecified | Invent an expansion, unique-user definition, or independent verification; omit the figure |
| “Review these labels; don't make changes.” | Explain or propose only | Edit files or publish a preview |
| “Tighten this one Play instruction.” | Edit the affected field and run focused checks | Rewrite About or run unrelated Travel stability soaks |
| “Ship the approved release; preview the new copy separately.” | Keep candidates separate, reuse exact evidence, honor guarded release/owner checkpoint and copy approval boundary | Mix unreleased copy into production; repeat successful checks without changed inputs |
| “Show the impact, keep it concise.” | Use supported outcome bullets and omit empty sections | Invent causal revenue claims or remove necessary consent/recovery details |
| “Are we done and is everything configured?” | Check live state and distinguish local implementation, matching validation, saved configuration, and deployed behavior | Call an unsaved monitor or an older SHA's passing build complete |
| “Use what our paid plan includes.” | Identify a measured benefit, preserve guardrails, and obtain any new access/subscription authority | Enable every product, connect a repository with automatic promotion, or treat usage alerts as an account-wide cap |
| “Keep the saved collection even when stale.” | Preserve accepted snapshots and timestamps; enforce actual permissions and explicit deletion paths | Apply the superseded six-hour Discogs cutoff |

| “The Fluence Moderns are in my FGN, not another purchase.” | Correct the instrument configuration, retain a legacy-ID review path and avoid counting pickups separately | Keep or auto-recreate a standalone pickup asset from Equipboard |
| “My Duo-Sonic might be 2016 or 2019, Desert Sand I think.” | Record owned family, null year and tentative finish | Assert a year or create a color-only catalog duplicate |
| “Pull my Equipboard; it only loaded one page.” | Compare a partial, account-bound snapshot and preserve local ownership | Delete unseen gear or promote Save to owned |
| “This custom part has no Equipboard page.” | Use the missing-catalog plan and official product source; distinguish standard part from custom configuration | Invent a slug, use a similar model or say a draft was submitted |

The current browser tests exercise visible Home reports, Source links, history,
keyboard and no-JavaScript access. Release-efficiency tests exercise full-range
coverage and evidence identity. Manual prompt review complements those tests;
it is not an independent model evaluation.
